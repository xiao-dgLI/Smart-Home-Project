# SmartHomeApp 项目规划书

> 版本：1.0
>
> 编制日期：2026-09-16
>
> 规划周期：10 周
>
> 适用范围：`android app/SmartHomeApp`

## 1. 项目概述

SmartHomeApp 是智能家居物联网系统的 Android 控制端，面向家庭用户和设备调试人员，提供环境传感数据展示、执行器控制、自动化规则、异常通知、项目与设备管理。应用同时支持新大陆云平台和 Wi-Fi/蓝牙本地连接，云端链路为 Android App ↔ NleCloud ↔ 网关/硬件设备。

### 1.1 当前技术基线

| 项目 | 当前状态 |
|---|---|
| 开发语言 | Kotlin 为主，少量 Java |
| Android 版本 | minSdk 26，targetSdk/compileSdk 35 |
| 构建工具 | Gradle 8.13，Android Gradle Plugin 8.13.1，JDK 17 |
| UI | XML + ViewBinding，单 Activity + 5 Fragment |
| 状态管理 | Android ViewModel + LiveData |
| 并发 | Kotlin Coroutines，同时存在 Handler/回调 |
| 网络 | OkHttp 4.12.0，HTTP API + TCP |
| 本地数据 | SharedPreferences + Gson |
| 后台任务 | Foreground Service 轮询 |
| 测试 | 仅有 Android 模板级单元/仪器测试 |

## 2. 现状评估

### 2.1 已具备能力

- 云平台登录、自动登录、项目创建/删除、设备创建/删除。
- 传感器卡片展示、单位格式化、设备在线状态和实时数据轮询。
- 云端与本地执行器开关，失败时状态回滚。
- 条件规则、定时规则的创建、启停、删除与云端同步。
- 阈值告警、人体感应告警和前台服务通知。
- GitHub Release 更新检查、APK 下载与安装流程。

### 2.2 主要问题

| 级别 | 问题 | 影响 |
|---|---|---|
| P0 | 开关状态与云平台状态存在不一致 | 用户可能误判设备真实状态 |
| P0 | 策略可能创建成功但不执行 | 自动化核心能力不可信 |
| P0 | 账号、密码、传输密钥保存在普通 SharedPreferences | 设备丢失或备份时有凭据泄漏风险 |
| P1 | `MainViewModel` 约 1,850 行，项目、设备、规则、连接、通知职责集中 | 修改风险高，难以单元测试 |
| P1 | Fragment 和 `NleCloudManager` 体积偏大 | UI、网络和业务逻辑耦合 |
| P1 | 网络调用混用 suspend、回调和 Handler | 取消、超时、重试与错误传递不统一 |
| P1 | 通信日志和部分页面依赖切页刷新 | 调试信息滞后，用户体验不稳定 |
| P1 | 自动化测试基本缺失 | 重构和发版缺乏回归保障 |
| P2 | 部分中文注释/日志存在编码异常 | 维护性与现场调试效率下降 |
| P2 | Release 未启用代码压缩，缺少 CI 和签名流程说明 | 产物体积、可追溯性与发布稳定性不足 |

## 3. 项目目标

### 3.1 总体目标

在不改变现有硬件和 NleCloud 接入方式的前提下，用 10 周完成一次“稳定性优先”的 2.0 升级，使设备状态、规则执行和告警链路可验证、可恢复、可追踪。

### 3.2 可量化指标

- 核心流程成功率：登录、项目加载、设备控制、规则同步在稳定网络下达到 99% 以上。
- 状态一致性：云端执行器真实状态在 3 秒内反映到 UI，失败操作 1 秒内回滚并提示。
- 稳定性：8 小时前台/后台轮询无崩溃、无持续内存增长、无重复告警风暴。
- 测试：核心 domain/repository 逻辑单元测试行覆盖率达到 70% 以上，核心用户旅程具备仪器测试。
- 性能：冷启动至首屏可交互时间不高于 2.5 秒，常规轮询不造成明显掉帧。
- 安全：仓库零明文真实凭据，本地敏感凭据使用 Android Keystore 保护。

## 4. 产品范围

### 4.1 2.0 必须交付

1. **可靠连接**：登录态统一、Token 过期恢复、指数退避重试、网络状态感知。
2. **设备一致性**：创建/删除后立即刷新，开关命令具备发送中、成功、失败和超时状态。
3. **规则可信**：本地草稿、云端 ID、启停状态明确分离，支持失败重试和执行记录。
4. **告警治理**：阈值防抖、静默期、离线判定、通知点击返回对应页面。
5. **安全存储**：凭据迁移到 EncryptedSharedPreferences/Keystore，备份规则排除敏感数据。
6. **工程质量**：核心模块拆分、统一错误模型、自动化测试、CI 构建、发布检查清单。

### 4.2 本期不做

- 不更换 NleCloud 平台或改造硬件通信协议。
- 不在 2.0 同期全量迁移 Jetpack Compose。
- 不引入复杂的多租户、家庭成员权限和商业化计费。
- 不开发 iOS 或 Web 客户端。

## 5. 目标架构

```text
UI (Fragment + ViewBinding)
        ↓ UiState / UiEvent
Feature ViewModel
        ↓ UseCase
Domain（Device / Sensor / Rule / Alert）
        ↓ Repository 接口
Data（NleCloud API / TCP / Local Connection / Secure Storage）
        ↓
OkHttp + Coroutines + Foreground Service
```

### 5.1 重构原则

- 按 Dashboard、Control、Rule、Notification、Settings 拆分独立功能状态，`MainViewModel` 仅保留全局会话与导航所需状态。
- 网络层统一为 `suspend` API，用受控的 `Result`/sealed error 表达错误，禁止无声吞异常。
- 设备、传感器和规则以唯一云端 ID 为数据源，UI 不自行维护第二份真值。
- 将轮询生命周期、重试、超时、防抖和离线判定集中到数据层。
- 引入依赖注入（优先 Hilt），让 Repository、时钟和网络客户端可替换、可测试。

## 7. 测试与验收

### 7.1 测试分层

- **单元测试**：传感数据格式化、规则表达式、阈值判定、状态机、重试策略。
- **Repository 测试**：使用 MockWebServer 覆盖成功、业务错误、HTTP 错误、超时、空数据和畸形 JSON。
- **UI 测试**：登录→选项目→查看传感器→切换执行器→创建规则→接收告警。
- **系统测试**：飞行模式恢复、Wi-Fi/移动网切换、锁屏、后台清理、设备离线、服务端限流。

### 7.2 核心验收用例

1. 云设备离线时禁止误操作，重新上线后自动恢复。
2. 开关命令超时后 UI 回滚，刷新后与云端终态一致。
3. 删除传感器、执行器或设备后，相关卡片、规则引用和本地缓存同步清理。
4. 规则创建后能查询云端 ID，启停与实际执行结果可追踪。
5. 应用在后台或锁屏时仅对有效传感器发告警，不因轮询重复发送。
6. 升级安装后旧数据正确迁移，不丢失项目、卡片和通知配置。

## 8. 安全与隐私

- 禁止将账号、密码、Token、SecurityKey、签名文件和 `local.properties` 提交到仓库。
- 敏感数据使用 Android Keystore 加密，并从 Android Auto Backup 中排除。
- 日志默认隐去 Token、账号、设备密钥和详细请求体。
- 保持 HTTPS；如 TCP 链路无法加密，需在文档中明确风险并限制其承载的敏感信息。
- 发布前执行依赖漏洞、敏感信息、Manifest 导出组件和网络安全配置检查。

## 9. 发布与运维

- 主分支保护：合并前必须通过静态检查、单元测试和 Debug 构建。
- 版本规则：`versionName` 使用语义化版本，`versionCode` 每次发布严格递增。
- 发布产物：带签名 APK/AAB、SHA-256、更新日志、回归结果、已知问题和回滚方案。
- 可观测性：统一错误码和通信日志，保留最近有上限的本地诊断信息，支持用户主动导出。
- 灰度顺序：开发设备→内测用户→小范围真实设备→全量 GitHub Release。

## 10. 风险与应对

| 风险 | 应对措施 |
|---|---|
| NleCloud API 文档与实际返回不一致 | 保留脱敏样例，用契约测试固化实际响应 |
| 轮询频率过高导致限流和耗电 | 动态轮询间隔，后台降频，失败指数退避 |
| 重构期间产生回归 | 先补特征测试，再分层拆分，每阶段保持可发布 |
| Android 后台限制导致轮询中断 | 核对前台服务类型与权限，加入恢复测试与用户可见状态 |
| 老用户数据结构变更 | 为每个本地模型增加 schema 版本和可回滚迁移 |
